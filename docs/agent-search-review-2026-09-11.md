# 通用 Agent 与 SearXNG 排查、修复记录

## Exa API 接入（后续新增）

重新构建并部署 API 与管理端后，在「系统配置 → Agent 联网搜索」选择「Exa Search API」，填写独立的「Exa API Key」，点击「测试搜索连接」，通过后保存配置。密钥可在 [Exa 控制台](https://dashboard.exa.ai/) 获取。连接测试会调用真实搜索并消耗服务商额度。

使用官方 `POST https://api.exa.ai/search`，标准 `auto` 搜索，获取每条结果的相关摘录、来源链接和发布时间；支持新闻分类、指定域名和最近一天/一周/30天/365天的发布时间过滤。请求格式依据 [Exa Search API 文档](https://exa.ai/docs/reference/search)。不自动调用 Deep Search 或 Exa Agent。

配置项 `web_search_exa_api_key` 独立保存并沿用后台密钥脱敏规则，不覆盖 Tavily、Brave 或 RedFox 密钥；系统配置支持自动新增字段，无需数据库迁移。原有超时、每日额度、缓存、引用和计费流程继续生效。Exa 作为独立服务商使用，已有 hybrid 模式仍为 SearXNG → Tavily。

验证：后端 `go test ./...`、管理端 TypeScript 检查通过。新增测试覆盖 Exa 请求鉴权、四种时间范围、域名过滤、摘录解析、无结果、HTTP 401/429/500、异常响应及请求取消。尚未配置真实 Exa Key，因此没有宣称完成 Exa 在线联调。

## 已确认的问题

1. **本地搜索上游不可用。** 直接请求本机 `127.0.0.1:8888/search`，Brave 返回 `Suspended: too many requests`，DuckDuckGo 返回 `CAPTCHA`，没有结果。容器存活和 JSON API 可访问不代表上游能搜索。生产使用同一份引擎配置，但本次没有连接生产环境，不能据此断言生产故障完全相同。
2. **回退条件检查错了层级。** SearXNG 只判断原始结果非空；即使结果随后被安全、相关性或域名过滤全部删除，也不再尝试放宽时间和新闻分类。地址查询参数中的旧过滤条件也可能在回退时残留。
3. **错误信息丢失。** 服务层没有读取 `unresponsive_engines`，普通会话又把错误压成“模型知识继续回答”，既不利于诊断，也容易让用户误以为实时信息已得到处理。
4. **规则代替语义。** 快速搜索路由把未命中关键词的问题一概判成无需搜索；含“最新”的指代追问可能在理解前文之前直接发起检索。
5. **检索主题被稀释。** 技术、新闻类具体问题被自动扩展为全球科技、综合头条。多搜的结果未必回答原问题，还增加请求量与上游限流压力。
6. **提示词存在冲突。** 一面要求完整正文，一面要求所有 reply 简短描述动作；通用问答还携带大量视频创作指导，容易出现预告多、直接回答少的体验。

## 本次修改

- 公共 SearXNG 配置增加 Bing。本地重启后真实检索恢复；原有安全及无关结果过滤仍然保留。试测 Google 同样要求 CAPTCHA，未将其加入最终配置。
- 用清洗后的有效结果判断回退；清除旧类别和时间参数；修复带尾斜杠的反向代理路径拼接。
- 区分“无匹配结果”和“上游引擎不可用”。管理员搜索测试可获得引擎错误详情；会话展示不含内部地址的原因说明，并保留尝试的查询和耗时。
- 指代追问优先进入语义路由；没有明确本地处理依据的模糊问题也交给模型判断。写作、明确禁止搜索和已选内容的本地修改仍保留快捷路径。
- 只有泛新闻汇总保留多查询扩展，具体问题保留原主题。
- 明确普通分析、比较、建议也属于 Agent 职责；简短方案要求只用于媒体执行计划，文字任务交付完整内容。媒体执行确认、计费和参数校验继续由服务端控制。

## 验证

- `services/api` 下运行 `go test ./...`，全部通过；需要额外数据库环境的测试仍受原测试跳过条件限制。
- 新增回归覆盖：引擎限流/CAPTCHA、过滤后回退、旧查询参数、反向代理路径、指代追问、具体检索不扩散。
- 通过真实服务层调用本机 SearXNG：`人工智能`、`Go programming language`、带 `news/day` 过滤的 `科技新闻`，三组均返回 5 条通过应用过滤的结果。此验证证明搜索链路可用，不等同于每条新闻均发表于当天；放宽上游过滤后仍需核验来源日期。

```powershell
$env:SEARXNG_TEST_URL = 'http://127.0.0.1:8888'
go test ./internal/service -run TestSearXNGLive -count=1 -v
```

## 生效与限制

本机 SearXNG 配置已重启生效。Go 修改需要重新构建并重启 API；本次未替换正在运行的 API，也未部署生产。生产同步代码和配置后，应重启 SearXNG、重新部署 API，再从管理端运行真实搜索测试。不要仅以 `/healthz` 判断搜索可用。

地址以 **API 进程所在网络** 为准：仓库 Docker 网络内用 `http://searxng:8080`；本机宿主进程用 `http://127.0.0.1:8888`。容器内的 `127.0.0.1` 不是宿主机。

上游限流仍可能复发。SearXNG 是聚合器，应用修复不能保证各搜索引擎持续放行；如有可用的 Tavily 配置，可使用已有 hybrid 模式兜底。本次未修改密钥、未自动切换付费服务。出站代理需根据部署网络配置，参见 [SearXNG 引擎设置](https://docs.searxng.org/admin/settings/settings_engines.html)。

当前架构仍是“检索路由 + 搜索/读页 + 一次主规划 + 有限内容修复”，并非可自主循环调用任意工具的通用 Agent。本次修复的是可复现的检索与交互缺陷，不能仅凭测试保证所有模型输出都变聪明。新增语义路由可能增加一次模型调用及对应耗时/费用；可使用管理端已有的“模糊问题路由模型”选择合适模型。下一阶段宜用真实对话评估漏搜、无效追问、上下文保持和完成率，再决定是否增加有预算上限的二次检索。
